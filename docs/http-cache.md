# API 响应的 HTTP 缓存边界

应用的 `/api` 挂载路径统一设置 `Cache-Control: no-store`。该响应头在 JSON 解析、Host 校验、停机闩和会话校验之前设置，使登录、退出、当前账号、项目读取及错误响应遵循同一规则。它不改变认证、项目权限或会话恢复逻辑，也不全局关闭 ETag 或改变静态文件的缓存策略。

`no-store` 要求遵守 HTTP 缓存规则的接收方不要存储这次响应。它不会追溯清除浏览器或中间层已经保存的旧响应，也不能保证外部代理或服务提供方的行为。这里不处理浏览器前进后退缓存（BFCache）、页面内存、扩展或 Service Worker，不将显式 `force-cache` 的合成复现表述为当前 UI 默认请求已经泄露数据。项目读取仍必须由服务端逐次授权。

## 独立浏览器验证

`test/browser-http-cache.js` 是显式运行的测试，不加入默认核心测试集合。它使用真实 Express 应用、真实 loopback HTTP 和 Chromium 的原生 `fetch` 缓存行为；数据库连接由合成 pool 全面替代，不连接 PostgreSQL，不调用模型。合成读取结果只用于区分旧缓存正文与重新到达服务端的请求，不能证明真实数据库或生产身份系统的正确性。

验证同时记录显式 `force-cache` 与默认 `fetch`，以实际服务端计数、状态和合成身份/项目匹配布尔值区分缓存命中与重新授权。API 的成功与失败响应以及静态资源对照分别检查；测试不通过 Playwright 路由替换响应或关闭浏览器缓存来获得结果。登录材料、cookie、CSRF 和正文原值不进入报告。

修复前的独立 Chromium 复现中，显式 `force-cache` 在退出、切换账号或合成权限撤销后命中旧响应，四项目标断言失败；默认 `fetch` 对照仍正确重新校验。修复后 Node 22、24 各执行一次，均通过 14 项断言：退出后返回 401，换账号后返回新身份/项目，合成撤权后返回 403，且目标请求都实际到达服务端。每次 23 个 HTTP、5,321 字节正文、25 次合成 SQL，真实 PostgreSQL 查询与模型调用均为零，浏览器、服务、socket 和 pool 清理通过。此结果证明上述固定测试路径，不是所有缓存或生产部署的完整验收。

运行 `npm run test:http-cache`，可选 `CHROMIUM_PATH` 与 `HTTP_CACHE_OUTPUT`；默认报告目录为 `artifacts/browser-http-cache/run-*/`。固定边界为 24 个 HTTP、512 KiB 正文字节、4 分钟工作和独立 1 分钟清理；字节不含头部、wire、浏览器控制协议、SQL 或堆分配，计量不构成分配硬上限。Node 22/24 CI 均接入同一命令，分别归档 `http-cache`、`http-cache-node24`。远端执行结果仍须以对应报告和 CI 为准，本文不将尚未执行的 CI 作为通过证据。
