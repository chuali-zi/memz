# 页面详情回执与草稿保护

事实依据使用 `GET /api/projects/:p/facts/:id/provenance?version=已显示版本`。页面在展示前核对 fact 的 ID、主体、属性，以及 revision 的版本和值与列表记录一致。历史区域还核对已列出的修订 ID；不会在失败后省略 version 或改读当前版本。来源、修订、候选、提议者和批准者的必要字段须有效，候选预期版本须为该修订版本减一。

当前事实列表没有来源 ID，单条依据中的 candidate 也没有 source_id，因此页面不会凭空要求这些字段或用来源标题假装证明 ID 一致。项目权限和跨表来源连接由服务端执行；页面核对的是实际返回的字段和已知请求引用，不是生产认证或来源真伪判断。

候选比较仍使用已有 `GET /api/projects/:p/candidates/:id/source`，没有新增 `/comparison` 接口。初次核对、刷新核对和“用最新版本填写新候选”都在接纳前验证整份回执：候选 ID、主体、属性、值、预期版本和来源 ID 绑定原候选；来源 ID 与候选一致。状态可因并发审批变化，不强制等同旧列表状态。角色和不可信文本标记须有效。

无当前事实必须明确为 null，并按 v0 比较；存在当前事实时，其引用和版本须有效。comparison 的预期版本、当前版本及 matches 须与候选/current 对象相符。同一个来源 ID 的标题不能在同一回执中冲突；当前版本若引用该候选，则须对应已批准状态、下一版本及相同值和来源。不发明服务端未返回的项目 ID header 或文本长度约束；未使用的附加元数据不执行、不显示。

坏的初次或刷新回执显示明确失败和重试入口，不把其中的内容展示成有效依据。填写新候选时遇到坏回执，既有核对面板、草稿和已选来源保持不变。读取期间用户编辑或提交候选的保护仍生效；切换工作区后，旧代次和已移除行的晚响应不能回填新页面。来源内容以文本显示，其中所谓指令不会被执行，也不会自动提交或批准。

独立 Chromium 用例使用明确合成回执验证错绑、缺失或不一致引用、状态漂移、失败恢复、显式历史版本和 A→B→A 晚响应。它不调用模型或真实数据库写入；真实接口和 PostgreSQL 回归另行执行。
