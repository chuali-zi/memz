# 创建请求的幂等重试

目标仅是避免同一个逻辑创建请求因并发发送、网络重试或响应丢失产生重复来源/候选和重复审计。不是通用工作流引擎，不为登录、审批或其他接口增加幂等机制。

## 接口合同

`POST /api/projects/:p/sources` 与 `POST /api/projects/:p/candidates` 可带 `Idempotency-Key`。允许1–128个ASCII字符：字母、数字、点、下划线、冒号、连字符。空值、不合法字符或过长键返回400。未传键时保持原行为：每次合法请求都创建新记录。

幂等范围是 `(project_id,actor_id,operation,key)`。同一范围内，规范化后的业务输入相同则返回最初创建响应，状态仍为200，JSON字段和值相同（不承诺属性顺序）；不同输入返回409，不再写业务记录或审计。不同用户、项目、创建接口可使用同一个键，互不复用结果。请求仍需当前会话、CSRF及写权限，不能用旧键绕过权限检查。

输入签名基于验证后的固定字段数组：来源为 `[trim(title),trim(content)]`；候选为 `[trim(subject),trim(predicate),trim(value),整数source_id,整数expected_version]`。忽略的额外字段不参与签名，数字字符串与对应整数等价。使用SHA-256摘要，理论哈希碰撞不是零概率；不把该摘要当身份凭据或密码学不可篡改证明。

候选创建响应是当时的凭据：例如最初status=pending，之后获批，再重放创建请求仍返回原pending响应。查询当前状态必须重新读取项目数据，不应把创建回执当实时状态。

## 数据库事务与并发

`idempotency_requests` 表保存请求摘要与原响应，主键约束范围唯一。应用在与业务写入相同的READ COMMITTED事务内：

1. 重新检查用户当前项目写权限。
2. 按范围取得事务级advisory lock。
3. 查询已提交回执；相同摘要返回缓存内容，冲突返回409。
4. 若无回执，执行原业务插入及审计，然后插入回执，一起COMMIT。

同键并发请求在锁上等待；获锁后的新SELECT在READ COMMITTED下看见赢家的提交。失败回滚同时撤销业务、审计和回执，键可以重试。提交成功但HTTP响应丢失时，客户端重试同键可取得已保存响应。该性质依赖PostgreSQL事务与持续保存的回执，不是跨任意外部系统的“恰好一次”保证。

RLS只允许owner/member读取或插入自己在该项目的回执；无上下文不可见，应用角色无UPDATE/DELETE权限。回执含合成来源/候选内容的副本，随项目数据同样受权限保护。信任应用设置事务身份的边界不变。

## 浏览器行为与兼容性

页面对来源、候选及固定模拟候选生成随机UUID键。同一页面中相同路径和原始JSON内容的未完成请求共享键；不自动重试。业务发送前保留本次JSON快照，后续回执核对以实际发送内容为准，不以await期间已变化的对象或新草稿为准。

2xx只表示收到HTTP成功状态，仍须验证创建回执后才可清除本请求仍拥有的键并进入成功分支。来源核对正整数id（不超过2147483647）、路径对应project_id及trim后的title/content；候选还核对subject/predicate/value、source_id、expected_version与status=pending，数字表单值按服务端十进制整数规则比较（source_id≥1，expected_version≥0，均不超过2147483647），原始文本长度、NUL和Unicode合法性也须满足对应写入规则。来源选择、清除未改变的来源草稿和“候选已提交”提示都须在此后发生。附加字段可保持兼容，不能凭公开演示身份猜测actor，回执也不是数据库提交的独立证明。来源/候选的真实完整行形状见[本机HTTP合同](consumer-contract.md)。

网络/正文中断、超时、5xx或无法验证的2xx使该次尝试结果不确定，并保留原键。此状态在该键的生命周期内持续：之后即使收到合法403、409或其他4xx，也只能说明这次尝试被拒绝，不能否定先前可能提交的记录；继续保留原键，等待核实或取得匹配的创建回执。不会因权限被撤销或内容冲突自动换键。只有这个意图从未有过结果不确定时，合法4xx才可释放它仍拥有的键；验证匹配的2xx回执也可释放。验证成功后，再次发起新的创建动作会使用新键；改变路径或内容则是新意图，不是原未知请求的安全重试，应先核实前一次结果。

服务重启会清空服务端内存会话，但保持原页面可以保留草稿和未知创建的原键。当前会话代次的项目API返回完整有效401后，页面暂停变更，允许操作者用最初实际登录的固定演示账号手动重新登录；还须重新确认当前项目访问与写权限，核对未确认请求，再手动以原路径、原JSON和原键重试。恢复不自动创建或审批，不将403或viewer变成写权限。步骤见[浏览器同账号会话恢复](browser-session-recovery.md)；合成会话回归本身不证明真实服务重启恢复。

这些客户端键和草稿只在页面内存中保存，刷新、关闭页面或切换账号后丢失；页面恢复功能不保存密码，也不把幂等键或草稿写入持久存储，不是离线队列。外部客户端若要跨进程/刷新重试，应自行持久保存该逻辑动作的键；CLI/MCP仍按各自合同在每次调用登录并尝试退出，不会借用浏览器的内存恢复状态。旧客户端不传键继续工作。部署新版页面/服务前应先完成迁移002，否则带键请求缺少回执表会失败；不能以失败时退回重复写入来隐藏未迁移状态。

## 升级与限制

新数据库由schema.sql直接创建该表。已有数据库先备份并验证本次实际备份，再按README依次执行001、002、003；每个脚本独立事务，002增加表/策略/权限，不修改已有业务行。003保留成员行/角色/回执，只允许有效成员访问；不能通过幂等重放恢复被撤销的权限。002支持重复/并发执行，重复后保留现有回执。使用独立迁移锁防止两次首次建表竞争，锁等待和语句超时与001一致。

目前没有回执TTL或自动清理，也没有跨客户端的键生成协调。回执随创建增长；不得随意清理后继续承诺旧键可重放。相同内容但不同键仍可创建多个来源/候选，这是兼容性选择。没有加入全局锁或性能优越性承诺；不同键的哈希碰撞只增加串行等待。

## 可复现证据

`npm run test:migrations` 在原始旧库升级和全新schema两个临时库中运行 `test/idempotency.js` 五组真实PostgreSQL测试：

- 来源和候选分别12个并发HTTP同键请求，结果一致，业务与对应审计各一条。
- 内容冲突409，trim规范化可重放；用户/项目/操作隔离；无键仍产生独立创建。
- 读/写权限、RLS、伪造actor和禁止修改/删除回执；审批后重放仍返回原创建状态。
- 在 `pg_locks` 实际观察竞争连接等待advisory lock，放行赢家后第二个创建回调不执行。
- 注入业务写入后异常，业务/审计/回执全回滚；之后可用同键成功重试；非法请求不占用键。

升级测试另比较已有业务行、序列、策略与授权，并在写入回执后再次迁移验证回执保留。浏览器流程断言真实创建请求带合法键。测试不代表压力吞吐测量或完整故障注入认证。

早期还执行了负向对照：临时移除幂等锁后真实数据库回归失败，恢复后通过；临时改动未保留在实现中。

## 客户端重叠请求的键所有权

A/B共用K1，A先结束后，新的C可建立K2。B晚返回时只能删除仍属于K1的映射，不能删掉C的K2；否则C已提交但响应丢失后重试会错误使用K3。createRecord在验证匹配2xx或尚无不确定历史的4xx清理时，都先比较当前映射是否仍等于本请求key；带不确定历史的键不会因后续4xx释放。任何旧请求返回都不能抹去新键及其不确定状态。

早前三组client-idempotency.test.js直接执行实际public/app.js，验证旧成功/旧4xx晚返回及当时的键清理合同；本轮独立VM与合成Chromium回归另验证了不匹配2xx、不确定后4xx、发送JSON快照及旧键不能覆盖新键；这些mock回执不证明数据库实际提交，不能拿历史用例代替新增验证。真实Chromium另发四次请求：A/B为K1，C已在数据库提交后丢弃响应，D重试K2；断言两把键、两条来源、两条审计，且D重放C的ID。该场景对应两个有意的新建动作及各自重试，不宣称四次请求只应创建一条。浏览器报告checks.creationKeyRace记录结果；延迟/丢弃的是实际服务响应。
