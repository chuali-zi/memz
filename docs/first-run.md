# 首次启动与有限彩排

## 首次使用路径

1. 安装README列出的Docker Compose、Node和npm，进入仓库根目录运行npm ci。
2. 确认5432与3000端口可用，执行docker compose up -d --wait。全新数据库卷会由官方PostgreSQL入口执行db/schema.sql，包括创建memz_app、表、约束、RLS及种子；已有卷不重跑初始化。
3. 执行npm start，打开日志显示的地址。若3000已有服务，可用PORT=3001 npm start；不要因页面能打开就假设打开的是本次进程。数据库端口冲突需要先检查占用者，不能通过删除现有数据库解决。
4. 使用公开owner演示账号登录，按README初始流程完成20号v1→15号v2、旧版本409、外部候选驳回、viewer拒绝及other项目隔离。
5. 重复演示不重置数据，改用docs/demo-script.md的唯一主体流程。验证优先用test:system:evidence的临时库入口，不对已有演示库运行npm test。

服务首次登录成功只证明账号与会话工作；还应看到项目、来源和当前事实，才能确认数据库可用。此版本没有自动安装依赖或自动修复数据库配置。

## 此次有限复核

2026-11-04在Linux、Node24、Docker Compose2.40.3和本地已有postgres:16镜像下，新建独立Compose项目及空数据卷。为保留现有5432数据库，使用仅对本次项目生效的Compose覆盖文件，把容器5432映射到随机本机端口；应用通过DATABASE_URL连接该新库，并以PORT=33011启动。

实际执行了Compose首次初始化（未预先创建应用角色）、真实CLI启动、浏览器批准/冲突/驳回/权限隔离/会话失效恢复，以及独立临时库核心与迁移回归。初始化与列明流程通过。该次基础浏览器彩排仅生成01–08业务截图，不包含分页规模注入，不能冒充完整22图材料包；开发中报告也不作为干净提交证据。正式证据以提交后重新生成的系统、检索和完整UI报告及CI为准。

发现并复现：指定PORT后启动日志仍固定显示3000，可能把用户引导到另一个已运行实例。修复后使用实际监听端口生成地址；test/startup.test.js创建真实子进程，核对地址、登录并读取数据库项目。它由系统取证入口自动执行，不创建或删除用户数据库。

同时修正README：推荐验证流程改为临时库，避免首次读者为测试删除现有卷；材料包明确需要系统、检索、UI三类报告。

本次复核没有验证Windows shell、首次联网下载镜像、所有Node版本、远程公开部署或生产配置。Compose镜像标签仍为postgres:16，可能随上游更新；实际运行版本以原始取证报告为准。以上环境记录不是比赛评分或跨环境保证。
