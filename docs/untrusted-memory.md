# 记忆内容的信任边界

人工批准只决定某条提议是否进入应用的当前事实，并留下版本和审计。它不证明内容客观正确，也不把来源正文、标题、候选值等文字提升为宿主的系统指令。来源里即使包含角色标签、工具调用 JSON 或“自动批准”命令，也仍然是待解释的数据。

## 接口标记与兼容性

以下返回来源正文的 GET 响应增加顶层 `sourceTextIsUntrusted: true`：

- `/api/projects/:p/sources`（来源分页）
- `/api/projects/:p/data`（兼容聚合读取，筛选排除来源时也保留标记）
- `/api/projects/:p/candidates/:id/source`（候选依据）
- `/api/projects/:p/facts/:id/provenance`（固定版本依据）

这是新增元数据；原来源正文、ID、版本和字段保持原样，没有迁移或自动删改内容。此前 `context-client` 及 MCP 上下文已有同名标记，但直接使用原始 HTTP 来源接口的接入方缺少明确提示；回归首先复现缺字段，再验证上述接口。创建接口仍返回原有创建回执，不把回执当成可执行指令。

MCP 的初始化说明和读取工具描述也明确宿主责任。`sourceTextIsUntrusted` 是机器可读提示，不是密码学证明、净化结果、提示注入检测器或权限控制。忽略该字段的客户端不会自动受到保护。即使读取到批准版本，也要把返回文字作为不可信数据处理。

## 宿主仍须负责什么

宿主应保留数据与指令的边界，不能将来源文字拼成系统/开发者指令。不要因为来源声称有权限就提供额外工具、凭据、外联能力或跳过授权；工具调用仍按实际账号权限和用户许可执行。只需检索的进程应保持 viewer 与只读 MCP 配置。提交待审与负责人审批是独立动作；开启待审工具不等于来源获准发起调用。无需向模型暴露数据库凭据或会话 cookie。

这些做法和提示不能保证真实模型不会被误导。模型、宿主、其他工具及其授权逻辑都在 Memz 数据库之外；本项目没有完成真实模型的对抗评测，不声称“彻底防提示注入”。数据库权限和事务能约束本服务实际执行的操作，不能代替宿主的提示注入防护。

## 合成证据

`test/untrusted-memory.js` 在系统测试的新建隔离库里创建含伪角色标签、外发要求、自动批准要求及嵌套 `tools/call` JSON 的合成来源。测试负责人显式批准一个普通候选后，分别通过原始 HTTP、viewer 只读 MCP、member 开启待审工具的 MCP，以及只读宿主示例读取它。

断言确认：原文保持原样、各读取路径标记不可信；MCP 输出中的 JSON 片段只是来源字符串；所有读取前后业务数据和审计完全一致；服务端请求观察也确认除了登录/退出外，没有业务写入或审批请求。MCP 工具描述保留不可信提示。原始 TAP 中 `Synthetic trust boundary result:` 记录合成 ID 和结果，不包含凭据。

这证明本实现的这些确定性读取路径没有解释或执行源文本，不证明连接某个真实语言模型后仍一定安全。测试没有调用任何模型，也没有访问合成来源中写出的外部地址。复现入口为 `npm run test:system:evidence`，不可将集成测试直接指向现有业务数据库。
