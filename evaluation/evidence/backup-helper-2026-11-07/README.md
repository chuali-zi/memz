# Backup helper: real PostgreSQL verification

Observed on 2026-11-07 in the same memz cloud, using an already cached `postgres:16` image, PostgreSQL tools 16.15, one unique Compose project per attempt and no host ports. This is a synthetic engineering check, with no model calls or user data. The helper was not yet committed during these runs; its exact file SHA256 was `b77c774b04a7d5e84b09fbea6aacba21acb67204bacabb5ba142f2927062e2cb`, subsequently committed unchanged in `379b517`. No clean whole-repository evidence is claimed for these runs.

The helper produced private custom-format archives. The final attempt restored its actual 34,922-byte archive into an independent empty database, compared all eight table row counts/fingerprints and RLS policy definitions, and verified 0600 file / 0700 directory permissions. The test backup, owned Compose container and volumes were removed; the ordinary `memz-product-pg` test service was untouched. `passed.json` records the exact bytes/hash and 5,517 bytes of captured command output. Archive bytes are deliberately not retained.

Both earlier failed verification attempts are preserved. Attempt 1 recorded only a generic failure after a valid backup, so that report alone does not locate the failure. Attempt 2 added bounded diagnostic markers and located a `psql` comparison failure after `pg_restore` succeeded. The temporary verification harness had mistakenly included a nonexistent `users` table; the real schema has eight tables. The final runner corrected that harness table list and added an explicit restore-tool checkpoint. The located failure was in the harness, not an established backup-helper or restore defect. The first attempt remains unlocalized by its own report; it used the same erroneous table list, but that is supporting context rather than stage evidence. The failed reports were not rewritten. Each attempt confirms its owned backup and Compose resources were removed. Archive hashes differ because newly initialized synthetic timestamps/archives are not byte-deterministic.

`runner.py` is the exact final temporary runner snapshot. It contains the original `/workspace/memz` repository path, public synthetic fixture setup, bounded subprocess/response handling and owned-resource cleanup. To reproduce elsewhere, use a copy with that root adjusted, verify the helper hash, and provide Docker Compose plus a cached postgres:16 image. It creates only its own random Compose project, restores into its own empty database, and never runs the maintenance migrations on an existing database. A reproduction is a new observation, not the archived result.

This does not validate a user's actual backup, remote cluster roles/passwords, ongoing writes, PITR, disaster recovery objectives, production load, or an arbitrary supervisor. The existing `test/restore.test.js` remains the broader application restore/write-continuation regression.
