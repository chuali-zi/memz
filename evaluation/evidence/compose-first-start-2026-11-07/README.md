# First-start Compose readiness regression

Two actual runs in the selected memz cloud compare the original Unix-socket health command with the corrected TCP command. Both use only owned fresh synthetic volumes, no published ports, network_mode:none, cached postgres:16 with pull disabled, a four-second initialization gate, a private empty Docker client configuration and bounded cleanup. There are no model calls, application requests, user data or production timing claims.

`before-commit.json` is the author's run before committing the fix; `committed-files.json` is the independent root run after commit `b2245ac`, with the same exact runner and compose SHA256. These are original reports, not reconstructed values. The second run observed the original service healthy at 6443ms while TCP exited 2 and the initialization marker was absent; the corrected service was healthy at 16266ms with TCP ready and the marker present. The original service later completed too. Total second-run time was 16878ms, including cleanup; all owned containers, volumes and networks were confirmed absent. Timing depends on initialization and polling and is not a startup performance comparison.

The gate models initialization still in progress. It does not prove the application's schema, permissions, migrations or full business behavior are ready; check-setup and /health/ready remain separate. The initial temporary exploratory fixture failed to start for an unconfirmed reason, was cleaned up and is not used as evidence of this product defect.

Reproduce from the full repository containing `b2245ac` with Docker Compose and an already cached postgres:16 image: `node test/compose-first-start.js --execute`. Without the explicit opt-in the script refuses to create resources. It deliberately is not a *.test.js file; native-PostgreSQL core tests do not require Docker. The ordinary configuration regression is `node --test test/compose-readiness.test.js test/compose-safety.test.js`.

The opt-in runner records exact fixed stages, bounded error categories, image identity, tool version and cleanup counts, while suppressing raw stderr and configuration environment values. Its 39-second watchdog cannot guarantee successful cleanup during arbitrary daemon failure; a failed cleanup remains failure and names only its own fixture. Never delete the default project's volumes to reproduce this check.
